# Product Parser Standard

Этот стандарт нужен, чтобы все товарные парсеры давали одинаковую структуру данных и запускались безопасно: сначала маленький тест, потом категория, потом полный обход.

## Контракт результата

`detail_page` должен возвращать словарь:

```python
{
    "name": str,
    "vendor": str | None,
    "model": str | None,
    "typePrefix": str | None,
    "price": float,
    "old_price": float | None,
    "currency": "RUB",
    "description": str,
    "characteristics": [{"name": str, "value": str | list}],
    "main_image": str | None,
    "images": [str],
    "files": [str],
    "documents": [{"name": str, "url": str}],
    "models_3d": [str],
    "categories": [str],
    "donor": str,
    "donor_url": str,
    "group": str,
    "dateUp": datetime.datetime,
}
```

## Group

Поле `group` в результате товара - это не группа pyspider-проекта в Web UI.

Для Marketlab `group` означает целевую бизнес-базу MongoDB, из которой legacy API будет читать товары. Например:

- `group: "electronik"` -> API читает товары из базы `electronik`;
- целевая коллекция для нормализованных товаров: `electronik.parsed_products`.

Если пользователь не указал другое значение, для товарных парсеров использовать `electronik`.

Важно: pyspider также имеет свое поле `project.group` в интерфейсе проектов. Оно служит для группировки/lock в pyspider и не должно смешиваться с товарным `result["group"]`.

## Обход каталога

1. `on_start` открывает стартовый URL или список тестовых карточек.
2. `catalog_page` ищет подкатегории.
3. Если подкатегории есть, передает новое дерево категорий через `save={"tree": [...]}`.
4. Если подкатегорий нет, парсит товары на листинге и пагинацию.
5. `listing_page` передает карточке товара дерево категорий и, если есть, данные с листинга: цену, название, картинку.
6. `detail_page` собирает финальный результат.

Важно: путь категорий всегда хранится списком в `categories`, а не строкой.

## Тестовый режим

Для каждого нового сайта сначала делается проект `<name>_test`:

- не более 3-5 карточек;
- без рекурсивного обхода всего каталога;
- без записи во внешнюю боевую базу, если это не нужно для проверки;
- с `status=DEBUG` или `STOP` после прогона.

## Ассеты

Картинки и файлы нужно скачивать к себе, потому что donor URL может закрыться или измениться.

Правила:

- относительный URL приводится к абсолютному через URL страницы;
- имя файла строится стабильно от URL, например `sha1(url) + extension`;
- если файл уже существует, повторно не скачивать;
- в Mongo сохраняется публичный путь, например `/upload/spider/entero/images/<hash>.jpg`;
- главную картинку сохранять отдельно в `main_image`, остальные в `images`;
- файлы инструкций, PDF и архивы сохранять в `files`;
- документацию сохранять в `documents` как список объектов `{"name": "...", "url": "/upload/..."}`;
- 3D-модели сохранять в `models_3d` как список локальных публичных путей.

Документация отличается от обычных файлов тем, что у нее есть читаемое название: например `Инструкция`, `Сертификат`, `Паспорт товара`.

## HTML-описание

Описание можно хранить HTML, но перед сохранением нужно:

- удалить `script`, `style`, комментарии;
- убрать ссылки или заменить их обычным текстом;
- скачать картинки из описания и заменить `src` на локальный путь;
- не сохранять лишние inline-стили.

## Секреты

В код проекта нельзя вставлять:

- логины/пароли MongoDB;
- прокси с доступами;
- серверные приватные пути, если они отличаются по окружениям.

Использовать переменные окружения:

- `PARSER_MONGO_HOST`
- `PARSER_MONGO_PORT`
- `PARSER_MONGO_USER`
- `PARSER_MONGO_PASSWORD`
- `PARSER_MONGO_AUTH_SOURCE`
- `PARSER_PROXY`
- `PARSER_MARKET_GROUP`
- `PARSER_DOWNLOAD_DIR`
- `PARSER_PUBLIC_UPLOAD_DIR`
